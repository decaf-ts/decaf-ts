### decoration (`@decaf-ts/decoration` v0.18.3)

1. **Identity** — Directory `/workspaces/decaf-ts/decoration`; package `@decaf-ts/decoration`, version `0.18.3` (`package.json:3`), described as "Decoration and metadata mechanisms for decaf-ts" (`package.json:4`). License MIT; ESM-first (`"type": "module"`), engines `node>=20`, `npm>=10`. Source version constants are build placeholders: `VERSION = "##VERSION##"`, `COMMIT = "##COMMIT##"`, `FULL_VERSION = "##FULL_VERSION##"`, `PACKAGE_NAME = "##PACKAGE##"` (`src/version.ts:8-27`), replaced at build time.

2. **Purpose & role** — Provides two complementary, low-level capabilities that the rest of the decaf-ts stack builds on: (a) a centralized runtime `Metadata` store keyed by constructor symbols, backed by `reflect-metadata` for design-time type hints (`src/metadata/Metadata.ts:135`), and (b) a flavour-aware `Decoration` builder/registry that lets the same semantic decorator key resolve to different concrete decorators per "flavour" (e.g. framework) at runtime (`src/decoration/Decoration.ts:313`). It is a foundational leaf module: it has no `@decaf-ts/*` runtime dependencies (`package.json:95-97`) and is consumed by the higher-level decorator modules (`decorator-validation`, `injectable-decorators`, `db-decorators`, `transactional-decorators`).

3. **Dependencies** — Runtime dependency: `reflect-metadata@^0.2.2` (`package.json:96`, imported in `src/metadata/Metadata.ts:8`). Dev dependency: `@decaf-ts/utils` (used only by `tests/e2e/e2e.config.ts:1` for `getPackage`) and `@types/jest`. No other decaf modules are required at runtime. Downstream consumers (per monorepo layering): `decorator-validation`, `injectable-decorators`, `db-decorators`, `transactional-decorators` all depend on this package for `Metadata`, `Decoration`, the decorator helpers, and `DecorationKeys`.

4. **Architecture & structure** — `src/` is organized into four subsystems:
   - `src/constants.ts` — `DefaultFlavour` ("decaf"), `ObjectKeySplitter` ("."), the `DecorationKeys` enum (metadata token registry), `DecorationState` enum, and `DefaultMetadata`.
   - `src/metadata/` — the `Metadata` static store (`Metadata.ts`) plus `BasicMetadata`/`Constructor` types (`types.ts`). Owns nested-path get/set via `getValueBySplitter`/`setValueBySplitter`, constructor-chain inheritance merging, mirroring onto constructors, and library registration.
   - `src/decoration/` — the flavour-aware builder: `Decoration.ts` (builder + static registry + pending-decorator resolution engine), `flavourRegistry.ts` (`assignFlavour`), `metadataLink.ts` (global resolver registration indirection), `types.ts` (builder-stage interfaces).
   - `src/shared/core.ts` — the concrete decorator utilities (`metadata`, `metadataArray`, `prop`, `method`, `param`, `paramMetadata`, `propMetadata`, `methodMetadata`, `apply`).
   - `src/decorators.ts` — user-facing `uses` (flavour-assigning class decorator) and `description`, re-exporting the `shared/core` helpers.
   - `src/index.ts` — barrel re-exporting all subsystems plus `version`.

5. **Public API surface** — From the barrel (`src/index.ts:7-12`), grouped:
   - **Metadata store**: `Metadata` (static: `get`/`set`, `properties`, `methods`, `type`, `params`/`param`, `return`, `description`, `constr`, `flavourOf`, `flavouredAs`, `registeredFlavour`, `registerLibrary`, `libraries`, `key`, `Symbol`, configurable `splitter`/`baseKey`/`mirror`); `getValueBySplitter`, `setValueBySplitter`; types `BasicMetadata`, `Constructor`.
   - **Decoration builder**: `Decoration` (instance `for`/`define`/`extend`/`apply`; static `for`, `flavouredAs`, `setResolver`, `defaultFlavour`); `assignFlavour`; `resolveFlavour`, `registerFlavourResolver`, `registerPendingResolver`, `resolvePendingDecorators`; builder-stage interfaces `IDecorationBuilder`, `DecorationBuilderStart/Mid/End/Build`, `FlavourResolver`; types `DecoratorTypes`, `DecoratorFactory`, `DecoratorFactoryArgs`, `DecoratorData`, `ExtendDecoratorData`.
   - **Decorator utilities**: `metadata`, `metadataArray`, `prop`, `method`, `param`, `paramMetadata`, `propMetadata`, `methodMetadata`, `apply`, `uses`, `description`.
   - **Constants/types**: `DefaultFlavour`, `ObjectKeySplitter`, `DecorationKeys`, `DecorationState`, `DefaultMetadata`, `VERSION`, `COMMIT`, `FULL_VERSION`, `PACKAGE_NAME`.

6. **Key patterns & concepts** —
   - **Builder pattern with staged interfaces**: `Decoration` exposes `for(key) → define()/extend() → apply()`, modeled by `DecorationBuilderStart/Mid/End/Build` so the type system enforces call ordering (`src/decoration/types.ts:9-82`).
   - **Flavours & flavour resolution**: decorators are registered per `(key, flavour)` in a static `Decoration.decorators` map (`Decoration.ts:323-332`). At application time `Decoration.flavourResolver(target)` picks a flavour; if the resolved flavour has overrides they replace the base, otherwise the default-flavour base is used; extras (from default and/or resolved flavour) are appended (`Decoration.ts:806-861`). Default flavour is `"decaf"` (`constants.ts:10`).
   - **Deferred/pending decorator resolution**: because TS property/parameter decorators run before class decorators, member decorations are queued in a per-owner `TargetDecorationState` (`Decoration.ts:262-272`) and resolved lazily — synchronously when a flavour is known, or via a microtask (`scheduleDefaultResolve`, `Decoration.ts:490-501`) otherwise. `Metadata.get` also triggers `resolvePendingDecorators` for any PENDING constructor in the chain (`Metadata.ts:366-371`), so reads can have resolution side effects.
   - **Overridable decorator factories**: the `{ decorator, args }` form (`DecoratorFactoryArgs`) defers factory invocation and lets flavour overrides re-invoke the factory with the original args; metadata diffs and property-descriptor snapshots are recorded so entries can be reverted and re-applied when flavour changes (`Decoration.ts:385-458`, `1087-1138`).
   - **Centralized metadata store**: `Metadata._metadata` is a `Record<symbol, any>` keyed by `Metadata.Symbol(constructor)` (a `Symbol.for` of `toString` + name). Nested keys use `ObjectKeySplitter` ("."). Inheritance is handled by walking the prototype chain and deep-merging (`collectConstructorChain`, `mergeMetadataChain`, `Metadata.ts:415-456`).
   - **Mirroring**: when `Metadata.mirror` (default true) the metadata object is also exposed on the constructor as a non-enumerable, non-configurable, non-writable property under `DecorationKeys.REFLECT` (`__decaf`) (`Metadata.ts:585-596`).
   - **Global resolver indirection**: `metadataLink.ts` holds module-level `flavourResolver`/`pendingResolver` function pointers; `Decoration`'s static initializer registers its own implementations into them (`Decoration.ts:340-345`), decoupling `Metadata` from `Decoration` to avoid a circular import while still allowing `Metadata.get`/`Metadata.flavourOf` to trigger resolution.

7. **Lifecycle / configuration / environment** —
   - **Boot**: importing the package runs `Metadata.registerLibrary(PACKAGE_NAME, VERSION)` at module load (`src/metadata/Metadata.ts:638`) and the `Decoration` static block registers the flavour/pending resolvers (`Decoration.ts:340-345`). No explicit `init()` is required.
   - **Flavours**: `DefaultFlavour = "decaf"`. Classes get a flavour via `@uses(flavour)` (`src/decorators.ts:27`); the global resolver is replaced via `Decoration.setResolver(fn)` (`Decoration.ts:1039`). `Decoration.defaultFlavour` is a public mutable static (tests mutate it, e.g. `tests/unit/flavour-change-compatibility.test.ts:2`).
   - **Configurable knobs**: `Metadata.splitter` (default "."), `Metadata.baseKey` (default `DecorationKeys.REFLECT`), `Metadata.mirror` (default true), `Metadata.allowReregistration(value)` for library re-registration (`Metadata.ts:189-191`).
   - **Env vars**: none read by the module itself. `TEST_ROOT` env var is only used by the e2e test harness (`tests/e2e/e2e.config.ts:9`).
   - **Build-time substitution**: `VERSION`/`COMMIT`/`FULL_VERSION`/`PACKAGE_NAME` placeholders are replaced during `build:prod` (the committed `lib/` shows `VERSION = "0.18.2"`, `PACKAGE_NAME = "@decaf-ts/decoration"`).

8. **Data & control flow** — A typical `@decorator` application on a member: `apply()` returns a `wrapper` (`Decoration.ts:952`). When applied to a property/method it computes the `owner` constructor, ensures a default flavour if none is set, snapshots any factory `args` overrides, registers a `PendingDecorator` callback (which closes over `this.decoratorFactory(key, resolvedFlavour, argsOverride)`), calls `resolvePendingDecorators(owner)` (which either applies immediately if a non-default flavour is known, or schedules a microtask), then auto-tags the member via `prop()`/`method()` (`Decoration.ts:952-983`). When `decoratorFactory` runs it looks up `Decoration.decorators[key][flavour]`, falling back to the default flavour's `decorators`, collecting `extras` from the resolved (or default) flavour, then invokes each decorator in sequence, threading class-replacement constructors and method-replacement descriptors through (`Decoration.ts:796-920`). Reads via `Metadata.get(ctor, path)` resolve the constructor chain, trigger pending resolution for any PENDING ancestor, gather values per constructor, and deep-merge with child precedence (`Metadata.ts:363-383`, `435-456`). The `@uses(flavour)` class decorator assigns the flavour in the registry and either resolves pending decorators immediately (non-default flavour) or marks the owner pending (default flavour) (`src/decorators.ts:27-49`).

   - `tests/integration/` (`metadata-and-decorators.integration.test.ts`): end-to-end public-API tests without mocks (method/prop capture, description, mirroring, builder extras, register errors, duplicate library).
   - `tests/e2e/` (`decoration.e2e.test.ts`, `metadata.e2e.test.ts`, `decorators.e2e.test.ts`, `e2e.config.ts`): run against `src`/`lib`/`dist` via dynamic import (`TEST_ROOT`); decorator-application suites are skipped for non-`src` roots because decorators are statically resolved at compile time and would write to a different module's `Metadata` store than the dynamically loaded reader (`tests/e2e/decorators.e2e.test.ts:5-9`, `decoration.e2e.test.ts:21-22`).
   - Coverage: notably covers argument preservation, override/extend, flavour fallback, metadata inheritance merging, and `apply()` return-value threading. Gaps: the microtask-based `scheduleDefaultResolve` path and the metadata-diff revert/re-apply logic on flavour change (`revertMetadataDiff`/`restorePropertyDescriptor`) have no dedicated unit tests; `metadataArray` has only e2e coverage; static-method/getter accessor edge cases are only smoke-tested in e2e.

10. **Usage example** — From tests, minimal real examples:
   - Flavour-aware property decorator with override and `@uses` (derived from `tests/unit/flavour-override.test.ts:48-79`):
     ```ts
     import { Decoration, DefaultFlavour, Metadata, uses } from "@decaf-ts/decoration";

     const mark = (name: string, num: number) =>
       Decoration.for("TEST").define({
         decorator: (n: string, i: number) => (target: any, key?: string) =>
           Metadata.set(target.constructor, Metadata.key("mark", key!), { n, i }),
         args: [name, num],
       }).apply();

     Decoration.flavouredAs("2").for("TEST")
       .define({ decorator: (n: string, i: number) => (t: any, k?: string) =>
         Metadata.set(t.constructor, Metadata.key("mark", k!), "flavour2") })
       .apply();

     class A { @mark("first", 1) prop!: string; }
     @uses("2") class B { @mark("first", 2) prop!: string; }

     Metadata.flavourOf(A); // DefaultFlavour ("decaf")
     Metadata.flavourOf(B); // "2"
     ```
   - Capturing design types via `@prop`/`@method` and reading them (derived from `tests/unit/methods.test.ts:4-17`):
     ```ts
     import { method, Metadata } from "@decaf-ts/decoration";
     class MethodClass {
       @method() method(arg1: string): Promise<void> { return Promise.resolve(); }
     }
     Metadata.params(MethodClass, "method"); // [String]
     Metadata.return(MethodClass, "method"); // Promise
     ```

11. **Relationships** — Leaf module in the decaf-ts decorator stack. `Metadata`/`Decoration`/`DecorationKeys`/`DefaultFlavour` and the decorator helpers are the primitives that `decorator-validation`, `injectable-decorators`, `db-decorators`, and `transactional-decorators` build upon (they register their own decorators via `Decoration.for(...).define/extend(...)` and store/retrieve metadata via `Metadata`). The flavour mechanism is the integration seam: downstream modules register flavour-specific overrides (e.g. for different DB drivers or DI frameworks) and consumers tag classes with `@uses(flavour)`. `@decaf-ts/utils` is a dev-only dependency used by the e2e harness; `reflect-metadata` is the only runtime third-party dependency and is required for `design:type`/`design:paramtypes`/`design:returntype` capture (`src/shared/core.ts:29-33`, `84-88`, `175-184`).

12. **Consumer notes** —
   - **Global mutable state**: `Decoration.decorators`, `Decoration.flavourResolver`, `Decoration.defaultFlavour`, `Metadata._metadata`, and the `metadataLink` module-level resolver pointers are global singletons. Tests mutate `Decoration.defaultFlavour` and `Decoration["flavourResolver"]` directly; consumers must restore them (`tests/unit/flavour-fallback-metadata.test.ts:5-26` shows the save/restore pattern). Cross-test contamination is a real risk.
   - **Lazy resolution side effects**: `Metadata.get` will trigger `resolvePendingDecorators` for PENDING constructors (`Metadata.ts:366-371`), so reading metadata can mutate state and flush pending decorators.
   - **Microtask timing**: when no non-default flavour is resolved, pending decorators are flushed on `Promise.resolve().then(...)` (`Decoration.ts:495-500`); code relying on decorators having run synchronously after class declaration may need to `await`.
   - **Mirroring is one-shot**: `Metadata.set` only defines the `__decaf` mirror if it is not already owned (`Metadata.ts:586-588`); later metadata writes update the internal store but the mirrored reference stays the same object (since `innerSet` mutates the existing bucket in place), so mirroring remains consistent as long as the bucket object identity is preserved.
   - **Duplicate library registration throws** by default (`Metadata.ts:607-614`); `Metadata.allowReregistration(true)` opts out.
   - **E2E caveat**: decorator application tests only work against `src`; testing against `lib`/`dist` is limited to runtime API calls because decorators bind to the statically imported module's `Metadata` store.
   - **Build artifacts lag the declared version**: committed `lib/` reports `VERSION = "0.18.2"` while `package.json` declares `0.18.3` (see Inaccuracies). `sideEffects: false` (`package.json:104`) despite module-load-time `Metadata.registerLibrary` and the `Decoration` static initializer — consumers should be aware the package has load-time side effects that bundlers' tree-shaking assumptions may not honour.
   - **Maturity**: v0.18.x, actively used by the broader monorepo; API is small and stable but the pending-resolution machinery is intricate and undertested.

### decorator-validation (`@decaf-ts/decorator-validation` v1.22.2)

1. **Identity** — Directory `/workspaces/decaf-ts/decorator-validation` in the decaf-ts monorepo. Package name `@decaf-ts/decorator-validation`, version `1.22.2` (`package.json:2-3`), description `"simple decorator based validation engine"` (`package.json:4`). 2. **Purpose & role** — A decorator-driven validation and model framework: it lets you declare validation rules on class properties via decorators (`@required`, `@min`, `@pattern`, …), back them with a registry of `Validator` classes, and provides a `Model` base class with validation, (de)serialization, hashing, equality/compare, and a model registry for rebuild flows. 2. **Purpose & role** — A lightweight dependency-injection layer for the decaf-ts stack. It provides TS decorators to mark classes as injectable (singleton or on-demand) and to inject dependencies into class properties, backed by a static `Injectables` facade over a swappable registry. It sits below domain modules (e.g. `db-decorators`, `transactional-decorators`) as a foundational DI primitive, and builds on the `@decaf-ts/decoration` reflection framework. `src/index.ts:1-8` describes it as "a simple Injectables implementation to create singleton instances … and easily inject it into other objects."

6. **Key patterns & concepts**
   - **DB Model base class**: There is no dedicated `Model` subclass; instead `overrides/overrides.ts` monkey-patches `Model.prototype` and `Model` statics (via `declare module` augmentation in `overrides/Model.ts`/`Metadata.ts`) to add persistence semantics — `hasErrors(previousVersion, …exclusions)` runs normal validation then `validateCompare` against the old version; `segregate` splits transient props; `pk`/`pkProps` resolve the `@id` property from `DBKeys.ID` metadata; `merge` combines old+new for partial updates; `shouldGenerate` honours `allowGenerationOverride`. Importing `./overrides` (triggered by the barrel and by `Repository.ts:1`) is what activates these.
   - **Repository pattern**: `Repository<M,C>` (`repository/Repository.ts:106`) is abstract, implements `IRepository<M,C>`, and declares abstract `create/read/update/delete`. Concrete bulk methods (`createAll`/`readAll`/`updateAll`/`deleteAll`) default to `Promise.all(models.map(m => this.create(m,…)))` (`Repository.ts:184,334,464,671`). The constructor (`Repository.ts:145-164`) wraps `create/read/delete` with `wrapMethodWithContext` and `update` with `wrapMethodWithContextForUpdate`, so each call runs `*Prefix` → concrete op → `*Suffix`. Prefix methods build a `Context` via `Context.args`, instantiate `new this.class(...)`, run `enforceDBDecorators(...,OperationKeys.ON)` and `model.hasErrors()`; suffix methods run `enforceDBDecorators(...,OperationKeys.AFTER)`. Update prefix additionally reads the old model when `applyUpdateValidation` is set, optionally merges, and passes `oldModel` to ON/AFTER handlers and `hasErrors(oldModel)`.
   - **Context**: `Context<F>` (`repository/Context.ts:107`) wraps an `ObjectAccumulator` (immutable accumulate) holding `RepositoryFlags` (logger, timestamp, operation, validation toggles, parent/child contexts). `Context.args` (`Context.ts:204`) pops the last argument: if it is a `Context` it is reused, otherwise a new context is created via `Context.factory` (default `DefaultContextFactory`) and appended to args — this is how a caller can pass an explicit context or let one be created. `Context.from`/`Context.childFrom` build operation/child contexts. `Contextual<C>` is an opt-in interface exposing `context(operation, overrides, …)`; `Repository` does not implement it, so the `contextual` branch in `Context.args` is unused in the default flow.
   - **Operations registry**: `Operations` (static facade) lazily holds a single `OperationsRegistry` (`operations/Operations.ts:85-88`). `OperationsRegistry` is a nested cache keyed by `[className][propKey][compoundOperation][flavour][handlerName]` (`OperationsRegistry.ts:34-43`). `register` deduplicates by handler name (anonymous handlers are hashed with a console warning, `OperationsRegistry.ts:188-195`). `get` walks the prototype chain accumulating handlers and resolves the flavour bucket via `Metadata.flavourOf`, falling back to `Decoration.defaultFlavour` then the first available bucket (`OperationsRegistry.ts:153-180`). This supports inheritance/override of property hooks and "flavours" (alternative decorator implementations per model, exercised in `tests/unit/flavours.test.ts`).
   - **Operation decorators**: `@on`/`@after` are the primitives (`operations/decorators.ts:444,578`); `onCreate/onUpdate/...` are convenience wrappers selecting `DBOperations` groups. The `operation` factory (`decorators.ts:615`) reads/creates per-(prop,compoundKey) metadata via `Metadata.readOperation`, stores `mergeData` (groupsort + custom data) under `handlers[class][prop][handlerName]`, and registers the handler with `Operations.register` plus a `propMetadata` entry under `ModelOperations.OPERATIONS`. `BlockOperations`/`BlockOperationIf` store a predicate + targets under `OperationKeys.REFLECT + OperationKeys.BLOCK` for later conditional evaluation (targets normalized to `BlockOperationDescriptor` with `kind` `crud`/`bulk`/`statement`/`query`).
   - **Identity / sequence**: `@id()` composes `required()` + `readonly()` + id metadata (`identity/decorators.ts:13-21`). `@generated(type?)` marks DB-generated props; `Model.shouldGenerate` skips generation when `allowGenerationOverride` is set and a value already exists (`overrides.ts:278`). There is no built-in sequence/auto-increment generator in this module — generation is delegated to the driver; `@version()` sets the version to 1 on create and increments on update (`model/decorators.ts:318-355`), with optimistic-lock check when `applyUpdateValidation` is on.
   - **Overrides pattern**: `overrides/` uses `declare module "@decaf-ts/decorator-validation"`/`"@decaf-ts/decoration"` to add signatures, then assigns implementations at import time. `ModelBuilderExtensions.ts` monkey-patches `ModelBuilderImpl.prototype` to expose the same decorators fluently (used by `tests/unit/model-builder.extensions.test.ts`). The `./validation` side-effect import chain (`src/index.ts:7` → `validation/index.ts` → `validators/index.ts`) registers `ReadOnlyValidator`/`TimestampValidator` via `@validator(...)`.
   - **CRUD operator interfaces**: `CrudOperator<M>` is the minimal contract; `BulkCrudOperator<M>` extends it; `IRepository<M,C>` extends `BulkCrudOperator` and adds `class`. `Repository` implements `IRepository`. Drivers subclass `Repository` and supply the four abstract methods; the lifecycle (context, decorators, validation) is handled by the base.
   - **Validation**: `Model.hasErrors(oldModel?, …exclusions)` (`overrides.ts:67`) runs `validate` then, if an old model is supplied, `validateCompare` (`model/validation.ts:266`), which iterates validatable update props, deserializes serialized props, enforces `@list` for Array/Set, runs `validateDecorators` (looking up `UpdateValidator`s via `Validation.get`), recurses into nested models, and aggregates `ModelErrorDefinition`. `ReadOnlyValidator` (deep-equality mismatch) and `TimestampValidator` (new timestamp must be greater) implement `UpdateValidator.updateHasErrors`.

The constructor already Proxied `create`, so the call dispatches to `wrapMethodWithContext`'s `apply` trap (`wrappers.ts:91-105`): (1) `createPrefix(model, …args)` runs — `Context.args(CREATE, this.class, args)` either reuses a passed `Context` or builds one and appends it; `model = new this.class(model)`; unless `ignoreHandlers`, `enforceDBDecorators(repo, ctx, model, CREATE, ON)` (`utils.ts:50`) reads `ModelOperations.OPERATIONS` metadata via `getDbDecorators`, resolves handlers with `getHandlersDecorators`, groups/sorts them (`groupDecorators`/`sortDecorators`), and invokes each `handler.apply(repo, [ctx, data, key, model])`; unless `ignoreValidation`, `model.hasErrors()` is awaited and a `ValidationError` thrown on errors; returns `[model, ...args, ctx]`. 1. **Identity** — Directory: `transactional-decorators/` in the decaf-ts monorepo (`/workspaces/decaf-ts/transactional-decorators`). 2. **Purpose & role** — Provides a transaction-management and concurrency-control primitive layer for the decaf-ts stack: a `Transaction` class that models an atomic unit of work, a `@transactional` method decorator that transparently wraps methods in transactions, and lock implementations that serialize/queue transaction execution. It sits low in the foundation stack — it depends on `db-decorators`, `decoration`, `decorator-validation`, and `injectable-decorators`, and is intended to be consumed by higher layers (e.g. `core`) that build repository/persistence abstractions on top.

6. **Key patterns & concepts**:
   - **Lock-based concurrency model.** `Lock` (`locks/Lock.ts`) is a single-writer mutex: `acquire()` returns immediately if free (setting `locked=true`) or pushes a `LockCallable` resolver onto `queue`; `release()` shifts the next resolver and dispatches it via `process.nextTick` (Node) or `setTimeout(_,0)` (browser), otherwise clears `locked`. `SynchronousLock` wraps a `Lock` to protect its own internal state (`currentTransaction`, `counter`, `pendingTransactions`) and implements `TransactionLock`: on `submit`, if a slot is free (`counter > 0`) it decrements and fires the transaction; otherwise it queues the transaction and returns `transaction.wait()`. `release` clears the current transaction, calls `onEnd`, then either schedules the next pending transaction (via `nextTick`/`setTimeout`) or increments `counter`. Re-entrant submit (same `transaction.id`) re-fires without re-queuing (`SynchronousLock.ts:58-65`).
   - **Transaction class.** Holds `id` (`Date.now()`), `source`, `method`, `logs`, `metadata`, a `completion` promise resolved/rejected from `fire()`, and an `action`. `fire()` executes `action`, optionally wrapped in `applyGlobalTimeout` (only when `globalTimeout > 0`), and dispatches the completion promise exactly once (`initialFireDispatched` flag). `bindTransaction(next)` chains a new transaction onto an active one by transferring logs, reassigning `bindToTransaction`/`bindTransaction`, and replacing `action` — so the active transaction fires the latest bound action (`Transaction.ts:315-323`). `release()` is idempotent (`released` flag).
   - **ContextLock coordination / context binding.** `bindToTransaction(obj)` (`Transaction.ts:331-395`) introspects the constructor via `Metadata.transactionals`/`Metadata.properties`/`Metadata.type` (cached in `metadataCache` WeakMap), then returns a `Proxy` over `obj` whose `get` trap: (a) wraps transactional methods in an `apply` proxy that prepends `self` (the transaction) as the first argument; (b) recursively re-binds transactional-typed properties; (c) tags the proxy with `__transactionProxy`, `__transactionTarget`, and `DBKeys.ORIGINAL`, and registers it in the static `contexts` WeakMap so `Transaction.contextTransaction(proxy)` can recover the transaction.
   - **Transactional decorator.** `transactional(...data)` (`decorators.ts`) records metadata under `Metadata.key(TransactionalKeys.TRANSACTIONAL, propertyKey)` and replaces `descriptor.value` with a `Proxy` whose `apply` strips any leading `Transaction` instances from the args (the `transactionPrefixLength` scan), determines the active transaction either from the first arg or from `Transaction.contextTransaction(thisArg)`, and either chains onto the active transaction (`bindTransaction` + `fire`) or creates and `submit`s a new one. It is registered via `Decoration.for(TransactionalKeys.TRANSACTIONAL).define({decorator, args}).apply()`.
   - **Overrides pattern.** Because `decoration`'s `Metadata` is a third-party namespace, this module uses TypeScript declaration merging (`overrides/Metadata.ts`) plus runtime assignment (`(Metadata as any).transactionals = ...`) to add `transactionals`/`isTransactional`. `Transaction.ts` does `import "./overrides"` and `index.ts` re-exports `./overrides`, so importing the barrel applies the augmentation as a side effect — hence `package.json` `sideEffects` entries for the compiled `overrides/index` files.

8. **Data & control flow** — A typical decorated call (`@transactional()`):
   1. Caller invokes `repo.create(model)`. The decorator's `apply` proxy runs (`decorators.ts:52`).
   2. It scans `argArray` for leading `Transaction` instances (`transactionPrefixLength`); none here, so `invocationArgs = argArray` and `activeTransaction = Transaction.contextTransaction(thisArg)` (`decorators.ts:69-88`). With no bound proxy, `activeTransaction` is undefined.
   3. A new `Transaction` is constructed with an `action` that `Reflect.apply`s the original method against `newTransaction.bindToTransaction(thisArg)` and then calls `exitFunction` → `transaction.release()` (`decorators.ts:112-132`).
   4. `Transaction.submit(newTransaction)` → `Transaction.getLock().submit(transaction)` → `SynchronousLock.submit` (`Transaction.ts:252-254`). If `counter > 0`, it decrements and calls `fireTransaction`, which sets `currentTransaction`, invokes `onBegin`, and calls `transaction.fire()` (`SynchronousLock.ts:54-103`).
   5. `transaction.fire()` runs `action`; the original method runs against the bound proxy. Calls from within the method to other `@transactional` methods on `thisArg` are intercepted by the proxy, which prepends the active transaction as the first arg; the decorator then takes the `activeTransaction` branch, `bindTransaction`s a child transaction (replacing `action`) and `fire()`s it again, all under the same lock slot (`decorators.ts:90-110`).
   6. When the outermost action resolves, `release()` is called once (idempotent), which calls `SynchronousLock.release`: clears `currentTransaction`, runs `onEnd`, and either schedules the next pending transaction or increments `counter` (`SynchronousLock.ts:107-151`). `Transaction.run` and `Transaction.push` provide the same submit→fire→release lifecycle for non-decorated code paths (`Transaction.ts:129-224`).
